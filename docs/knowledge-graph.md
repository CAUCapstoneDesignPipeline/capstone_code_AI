# 지식 그래프의 키워드와 개념

상태: 정의만 있다 (코드: [`app/schemas/knowledge.py`](../app/schemas/knowledge.py), 시험: `tests/schemas/test_knowledge.py`).
정본은 팀 문서의 [회의록 10/30 지식 그래프 설계](../../docs/meetings/2026-10-30-knowledge-graph.md) 이고, 이 문서는 그 구조를 AI 쪽에서
어떤 필드와 검사로 옮겼는지만 적는다. 아직 API 계약에는 없다 (BE 와 맞춘 뒤 `ai-openapi.yaml` 에 올린다).

## 구조

```text
Keyword (노드)                       키워드 하나 = 노드 하나. 같은 뜻의 개념을 묶는다
  Concept 1: 설명 + 소스(페이지 구간)  키워드 안의 설명 1개
  Concept 2: 설명 + 소스
  ...
```

```json
{
  "keywordId": "…uuid", "name": "힙", "aliases": ["heap"],
  "concepts": [
    {"conceptId": "…uuid", "origin": "extracted",
     "explanation": "힙은 부모가 자식보다 작은 완전 이진 트리예요.",
     "sources": [{"noteId": "…", "noteVersion": 3, "span": {"startOffset": 120, "endOffset": 152, "quote": "…"}}]},
    {"conceptId": "…uuid", "origin": "generated",
     "explanation": "…",
     "sources": [{"noteId": "…A"}, {"noteId": "…B"}],
     "external": [{"url": "https://…", "title": "…", "retrievedAt": "2026-10-31T09:00:00Z"}]}
  ]
}
```

(`generated` 의 `sources` 는 줄여 썼다. 실제로는 첫 개념처럼 `noteVersion`·`span` 이 모두 들어간다.)

| 필드 | 뜻 |
| --- | --- |
| `Keyword.name` / `aliases` | 보여 줄 이름과 같은 뜻의 다른 표기 |
| `Keyword.concepts` | 1개 이상. 개념 없는 키워드는 만들지 않는다 |
| `Concept.origin` | `extracted` 노트에서 뽑은 개념 · `generated` 사용자가 모르는 지식으로 만든 개념 |
| `Concept.explanation` | 설명 1개 (최대 2000자, 임베딩 입력 한도와 같다) |
| `Concept.sources` | 개념이 나온 페이지(노트)와 구간. 구간은 기존 `Span` (원문 인용 포함) |
| `Concept.external` | 생성에 쓴 인터넷 자료 (URL·제목·가져온 시각·인용). 결과 카드에 URL 을 보이려고 남긴다 |

## 검사하는 것

- `extracted`: 소스는 페이지 하나, 외부 자료 없음.
- `generated`: 소스에 도출에 쓴 개념들의 페이지를 모두 넣고, **서로 다른 노트가 둘 이상**이어야 한다 (기능 명세 1.4 "복수 문서의 실질적 기여").
- 한 키워드 안에서 `conceptId` 는 겹치지 않고, `name` 이 `aliases` 에 또 들어 있지 않다.
- URL 은 `http(s)` 만 받는다. 모든 객체는 모르는 필드를 거절한다 (`Closed`).

여기서 확인하지 않는 것: 같은 뜻인지 (병합은 `/embeddings` + `/merge-decisions` 몫), 인용이 노트 원문과 일치하는지
(기존 `/extract` 의 구간 검사 몫), 설명이 근거에서 나오는지 (판정 몫).

## 정하지 않은 것과 모델이 남겨 둔 자리

| 미정 (회의록) | 모델에서 |
| --- | --- |
| 개념의 `etc` 필드 | 두지 않았다. 파이프라인이 필요로 하는 것이 생기면 그때 한 필드씩 추가한다 |
| 소스에 인터넷 URL 을 넣을지 | `sources` (페이지) 와 `external` (인터넷) 을 나눠 두었다. 넣기로 하면 합치면 되고, 안 넣기로 해도 결과 카드용 URL 은 남는다 |
| 결과가 새 키워드인지, 기존 키워드의 새 개념인지 | 둘 다 표현된다: `generated` 개념을 새 `Keyword` 에 넣거나 기존 `Keyword.concepts` 에 더하면 된다 |
| 거절한 조합의 기록 | 이 모델 밖이다 (개념 쌍과 시각을 따로 저장) |

## playground 에서 보기

`uv run python run_playground.py` → **키워드** 버튼 (`POST /dev/keywords`, 코드 `app/services/links/keywords.py`).
지금 노트 색인에서 키워드를 만들어 `Keyword` 스키마로 검증한 뒤 보여 준다 (LLM 호출 없음). 141개 노트에서 키워드 5,450개가 나오고
그중 216개가 3개 이상의 페이지에 걸친다 (신뢰도 0.35 이상).

- 묶는 기준은 노트 사이 연결과 같은 표기·별칭이다. **뜻이 다른 개념이 섞인다** (예: 정규화 표기가 같은 "Consistency" 가 ACID 의 일관성과
  휴리스틱의 일관성을 한 키워드로 묶는다). 같은 노트의 서로 별칭이 아닌 두 개념은 묶지 않는다. 같은 뜻인지 확정하는 병합 판정은 아직 연결하지 않았다.
- **키워드 및 설명 추출** (`POST /dev/extract`) 은 노트 하나에서 키워드와 키워드마다 설명을 뽑는다. 키워드·신뢰도는 `/extract` 와 같은 추출기이고,
  설명은 `app/services/concepts/describe.py` 가 노트에서 고른 문장 하나다 (모델이 쓴 글이 아니라 원문 구간). 고르는 순서: 키워드로 시작해 뜻을
  말하는 문장(`**X**: …`, `X는 …`) → 정의문 꼴 → 그 밖의 문장. 제목에만 나온 키워드는 제목 아래 첫 문장. 노트 141개에서 신뢰도 0.35 이상 키워드
  7,333개 중 95% 가 설명을 얻었다. 설명이 정의가 아닐 때도 많다 (그 키워드가 나오는 문장을 고른 것이다).
- **문서 연결** 은 기본으로 **키워드 노드** 를 보여 준다 (`POST /dev/keyword-graph`, `build_keyword_graph`). 선 = 두 키워드 사이에 증거가 있는 것이고, 증거는 세 수준이다
  (체크박스로 고른다, 기본은 앞의 둘):

  | 수준 | 증거 | 점수 |
  | --- | --- | --- |
  | 같은 문장 | 두 키워드가 한 문장에 같이 나온다 (8개 넘는 나열은 뺀다) | 1/(문장의 키워드 수 − 1) |
  | 제목과 본문 | 한쪽이 제목에 있고 다른 쪽이 그 절 본문에 나온다 (제목 키워드가 절의 주제). 제목에 같이 나온 둘도 | 0.5 |
  | 같은 문단 | 빈 줄·제목으로 끊긴 한 문단에 나온다 (키워드 10개 넘는 문단은 뺀다) | 0.3/(문단의 키워드 수 − 1) |

  같은 노트에서 이미 같은 문장으로 이어진 쌍에는 제목·문단 증거를 더하지 않는다. 문단·절 위치는 `app/services/links/layout.py` 가 가른다.
  "이 노트" 는 이 노트의 키워드 중 연결이 센 것과 그 이웃(다른 페이지에서 이어진 키워드)을, "전체 키워드" 는 둘 이상의 페이지에 걸치고 연결이 센 키워드 200개를 그린다.
  점을 누르면 이어진 키워드와 개념(설명 + 페이지), 선을 누르면 증거(수준 표시)가 나온다. 노드 종류를 **문서 노드** 로 바꾸면 같은 키워드에 개념을 넣은 두
  페이지를 잇는 사용자용 그래프(회의록 10/30)가 나온다.
- **추정 연결** (`levels` 에 `inferred`, `app/services/links/inference.py`): 문장·제목·문단 어디에서도 같이 나온 적 없는 키워드 쌍을 그래프 이론의 링크 예측으로 잇는다.
  체크박스 "추정 연결" 로 켜고 (기본은 꺼짐), 증거가 아니라 **추정** 이라서 선은 점선, 이 노트의 키워드에 이어질 만한 다른 키워드로 올라온 노드는 점선 테두리로 보인다.
  - **점수** = z(log(1 + 1000·Katz)) + z(의미 유사도). Katz = β·A² + β²·A³ (β = 0.05, A = 모든 증거 수준으로 이어진 키워드 그래프): 이미 이어진 키워드를 거쳐 두세 걸음에 닿는 정도.
    의미 유사도 = 키워드 벡터(그 요소 임베딩의 평균)의 코사인. 임베딩이 없으면 구조 점수만 쓴다. z 는 그래프마다 키워드 150개를 표본으로 모든 쌍에서 구한 평균·표준편차.
  - **고르는 규칙**: 키워드마다 (걸어서 닿는 키워드 ∪ 의미가 가까운 10개) 중 점수 3.0 이상의 상위 5개. 이미 증거로 이어진 쌍과 자기 자신은 뺀다.
    "이 노트" 범위에서는 이 노트의 키워드(상위 14개)에 대해 계산하고, 이어질 만한 다른 키워드를 키워드마다 상위 2개씩(모두 최대 10개) 노드로 더한다. "전체" 범위는 올라온 200개 안에서만 잇는다.
  - **근거 표시**: 공통 이웃(이웃이 적은 것부터 3개)과 의미 유사도. 관계가 실제로 있는지는 "경로까지 보고 관계 확인" 으로 경로의 문장을 보고 LLM 이 판정한다 (추정은 증거가 아니므로 선에서 바로 LLM 에 보내지 않는다).
    두 키워드 연결 탭에서도 증거로 안 이어진 쌍이면 추정 점수·공통 이웃을 보인다.
  - **비용**: 모든 쌍(N²)을 계산하지 않는다. 키워드 하나는 이웃 목록을 따라가는 두 걸음(numpy, 희소 벡터 × 이웃 목록)과 의미 벡터 한 번 곱으로 후보를 구하고, 화면에 올린 키워드에 대해서만 부른다.
    실제 노트에서 이 노트 추정 12ms, 전체 200개 279ms (임베딩이 디스크에 있을 때. 처음 임베딩은 1분쯤).
  - **평가** (키워드 5,198개 · 증거 연결 18,050개): 연결의 10% 를 가리고 되찾는 정도(AUC, 무작위 쌍과 구별) — 점수 0.992 (문장·제목만이면 0.980), Katz 만 0.978 (0.939), 의미만 0.886 (0.907),
    Adamic-Adar·공통 이웃·랜덤 워크는 0.97 안팎 (0.92). 쓸모 있는 새 지식 쌍(라벨 275쌍 중 30개)을 올리는 정도는 이 점수 0.729, 랜덤 워크 0.738, Katz 0.725, 의미만 0.632 로 참고 수준이다.
    이미 이어진 쌍은 쓸모가 오히려 낮았다 (6% 대 11%) — 안 이어진 쌍을 잇는 이유다. 가린 연결 되찾기는 무작위 쌍과 가르는 쉬운 시험이라 "쓸모 있다" 는 뜻이 아니다.
  - **한계**: 키워드 묶음이 표기 기준이라 뜻이 다른 개념이 섞이면 추정도 틀린다 (예: "Consistency" 가 ACID 일관성과 요구사항 쪽 일관성을 섞어 "요구사항 분석" 과 이어졌다).
    쓸모 있는 쌍이 30개뿐이라 방법 사이 순위(0.73 대 0.74)는 구별되지 않는다.
- **두 키워드 연결** (오른쪽 패널의 탭, `POST /dev/keyword-connect`): 아무 두 키워드나 검색해 골라 직접 증거와, 다른 키워드를 거치는 **가중 경로** (`app/services/links/paths.py`) 를 본다.
  그래프에 그리지 않은 키워드도 된다.
  - **비용으로 고른다** (이전: 2~3걸음만, 이웃이 아주 많은 허브는 건너뜀, 이웃은 점수 상위 25개만 → 4걸음 이상이거나 허브를 거치는 관련을 놓쳤다).
    선 비용 = 1/(0.2 + 증거 점수) (같은 문장처럼 강한 증거는 싸고 문단은 비싸다), 중간 키워드 비용 = 0.5·log2(1 + 이웃 수) (허브는 건너뛰지 않고 비싸게 친다, 이웃 100개면 +3.3),
    길 비용 = 합. 6칸·비용 10 까지.
  - **서로 다른 길 최대 6개** (싼 순): 가장 싼 길을 찾은 뒤 쓴 중간 키워드의 비용을 1.6배로 올려 다시 찾는다 (같은 길의 변형을 늘어놓지 않으려고). 직접 선은 쓰지 않는다 (직접 증거는 따로 보인다).
    허브를 지난 길은 표시한다.
  - **고른 값** (라벨 275쌍 + 무작위 400쌍): λ=0.5·최대 비용 10 이면 쓸모 있다고 한 쌍의 90% 에서 길이 나오고 무작위 쌍은 5% 만 나온다 (이전 방식은 77% 와 3%).
    실제 엔드포인트로 재면 쓸모 있는 쌍 87% (이전 77%), 같은 노트의 쌍 60% (58%), 무작위 쌍 4% (3%), 한 쌍에 6~15ms (이전 3ms).
    쓸모 있는 쌍의 40% 는 허브를 지나는 길을 가졌고 (이전 방식이 버리던 길), 가장 싼 길은 대개 허브를 피한다.
    가장 싼 길의 비용으로 쓸모 있는 쌍을 올리는 정도는 AUC 0.73 으로 Katz·랜덤 워크와 비슷하다 (쓸모 있는 쌍 30개라 구별되지 않는다). λ 0 → 0.3 → 0.6 이면 0.709 → 0.725 → 0.728.
  - 정확성: 작은 그래프에서 모든 단순 경로를 다 세어 가장 싼 비용과 같은지 시험한다 (`tests/services/test_paths.py`).
- **관계 확인 (LLM)** (`POST /dev/keyword-relation`, `app/services/links/relation_llm.py`, `kwrel-llm-1`): 선이나 두 키워드 연결에서 버튼을 눌렀을 때만 부른다.
  두 키워드의 설명과 증거(직접 증거, 또는 중간 키워드를 거친 `path` 증거)를 보내 `related`(관계 있음) · `weak`(약함, 간접) · `unrelated`, 관계 유형
  (is_a · part_of · causes · requires · used_for · contrasts_with · example_of · analogous_to · related), 방향, 이유를 받는다. 노트 밖 지식으로 관계를 만들지 않고,
  판정마다 증거 id 를 인용해야 하며 (없으면 `unsure`), 직접 증거를 인용하지 못한 `related` 는 `weak` 로 낮춘다. 결과는 디스크에 캐시한다
  (`data/private/cache/keyword-relations`). 모델은 `AI_KEYWORD_RELATION_LLM_*` → `AI_LLM_*` → `ANTHROPIC_API_KEY` 의 기본 모델 (effort low) 이다.
  이 호출만 노트 내용을 LLM 제공자에게 보낸다 (로컬 접속만 받는다).
  141개 노트 (신뢰도 0.35 이상) 에서 DB-WAL 의 "WAL" 과 "Consistency" 는 직접 증거가 없고 ACID 를 거치는 길만 있는데, 모델은 `weak` 로 판정했다
  ("WAL 은 ACID 중 Atomicity·Durability 를 달성하고 Consistency 는 ACID 의 한 요소로만 나온다 — 간접 관계").
  같은 문장·문단 공동 출현은 관계의 증거일 뿐 관계 자체가 아니다 (나란히 나왔다고 관련 있는 것은 아니다). 그래서 이 확인이 따로 있다.

- **지식 제안** 은 새 지식 = **키워드 A 의 요소 + 키워드 B 의 요소 + 인터넷 지식** 을 만든다 (회의록 10/30 "사용자가 모르는 지식 생성"). 세 단계이고, 둘째·셋째만 모델 제공자를 부른다:
  1. **후보 쌍** (`POST /dev/proposals/candidates`, `app/services/links/pairing.py`, 결정적): 이 노트의 요소(키워드마다 설명 하나)와 다른 노트·다른 키워드의 요소를 잇는다.
     신호는 공유 낱말(2개 이상) · 공통 키워드 언급 · 임베딩 근접(로컬 bge-m3) 셋이고, 겹칠수록 앞에 둔다. 임베딩이 있으면 코사인 0.5 미만은 뺀다
     (실제 노트 275쌍을 AI 라벨러 둘이 눈가림으로 평가했을 때 0.5 미만 89쌍 중 쓸모 있는 쌍이 없었다). 혼자 읽을 수 없는 요소(너무 짧거나 앞 문장에 기대거나 표 칸)는 뺀다.
     같은 문장을 가리키는 중복은 한 번만 낸다. 임베딩은 처음 한 번 1분쯤 걸리고 `data/private/cache/element-embeddings.npz` 에 남는다. 받아 둔 모델이 없으면 임베딩 없이 돈다.
  2. **LLM 선별** (`POST /dev/proposals/screen`, `pair_screen.py`, `pairscreen-llm-1`, 눌렀을 때만): 두 문장으로 둘 어느 쪽에도 없는 구체적이고 맞는 결론이 나오는지 다섯 라벨
     (useful · vague · redundant · unrelated · unusable)로 묻는다. AI 라벨러와 비교하면 useful 로 고른 쌍의 35~44% 가 라벨러도 useful 이라 했고 (거르지 않으면 11%)
     라벨러가 useful 이라 한 것의 40~50% 만 찾는다. 놓치는 쌍이 있으므로 걸러진 후보도 접어서 보여 준다.
  3. **새 지식 만들기** (`POST /dev/proposals/generate`, `generate.py`, `newknowledge-llm-3`, 눌렀을 때만): 두 문장을 주고 웹 검색(`web_search_20250305` 기본판, 검색은 한 번)으로 이어 주는 자료를 찾게 해
     해요체 결론을 받는다. 모델 말을 그대로 믿지 않고 코드가 확인한다: 외부 출처 URL 은 이 호출의 검색 결과에 실제로 나온 것만 남기고, `fromA`·`fromB` 는 노트 문장에서 그대로 옮긴
     부분이어야 하며, 결론이 노트 문장과 거의 같으면 새 지식이 아니다(known). 하나라도 어기면 가설(held)이고 이유를 보인다. 통과하면 `generated` 개념으로 만든다 (소스에 A·B 의 페이지, `external` 에 URL).
  **자동 생성**: 후보 쌍이 나오면 LLM 선별을 하고 상위 3개의 새 지식을 바로 만든다. 두 키워드 연결 탭에서 두 키워드를 이으면 그 둘의 요소 쌍(서로 다른 노트의
  혼자 읽을 수 있는 설명 중 공유 낱말이 많은 쌍)으로 바로 만든다. 체크박스로 끌 수 있고 (브라우저에 기억), 끄면 버튼을 눌렀을 때만 한다. 자동은 이어진 쌍마다 하지 않는다 —
  선택한 한 쌍이나 노트당 상위 3개뿐이라 LLM·웹 검색 횟수가 후보 수나 선 수에 따라 늘지 않는다. 같은 쌍은 저장된 결과를 쓴다.
  **비용**: 모든 요소 쌍(E²/2)을 비교하지 않는다. 색인은 글자 수에 비례해 한 번 만들고 (낱말 역색인, 키워드 이름 trie), 요소마다 신호가 가리키는 몇십 개만 본다 (낱말·키워드 빈도 상한).
  임베딩 근접은 A×E 행렬곱 한 번 + 정렬 없는 top-k 이고 E×E 행렬은 만들지 않는다. 실제 노트 3,318 요소 전부를 질의로 후보를 찾는 데 6.9초 → 0.57초 (후보 수 동일),
  그래프·연결 요청은 선 색인을 증거 수준마다 캐시해 50~130ms → 1~5ms. 군집 근사 색인(IVF)도 시험했지만 실제 임베딩에서는 재현율 0.95 에 전체의 46% 를 훑어야 해서 정확한 검색을 쓴다
  (요소가 수십만이 되면 `_nearest_all` 자리에 HNSW 를 꽂는다).
  **진행 상황 (SSE)**: 새 지식 만들기는 `POST /dev/proposals/generate/stream` 이 `text/event-stream` 으로 진행을 그때그때 보낸다 (화면이 쓰는 쪽, 같은 일을 하는 `/dev/proposals/generate` 는 그대로).
  이벤트: `start`(모델·검색 도구) · `cached` · `thinking` · `search_start` · `search`(검색어) · `search_results`(받은 페이지 목록) · `writing`(글자 수, 200자마다) · `validating`(출처 수) · `result`(결과) · `error`. 모두 `t`(시작 뒤 초)가 있고, 10초 동안 조용하면 `: keep-alive` 주석을 보낸다.
  카드에는 단계가 줄로 쌓이고 (✓ 끝난 단계, 돌아가는 단계), 검색어와 받은 페이지가 보인다. 실제 한 쌍에서 시작 0초 · 생각 1.6초 · 검색 3.5초 · 결과 9개 12.5초 · 쓰기 12.5~16.5초 · 확인 16.9초였다 — 대부분의 시간이 검색 대기라는 것이 화면에서 바로 보인다.
  **토큰 스트리밍 (LLM 응답이 보이는 모든 곳)**: 모델이 글을 쓰는 대로 화면에 이어 붙는다.

  | 화면 | 엔드포인트 (SSE) | 무엇이 쓰이는 대로 오나 |
  | --- | --- | --- |
  | 새 지식 만들기 | `POST /dev/proposals/generate/stream` | `field` 이벤트: `newKeyword`·`conclusion` (가설이면 `reason`) |
  | LLM 선별 | `POST /dev/proposals/screen/stream` | `pair` 이벤트: 쌍마다 `label` (나오는 대로)과 메모 `conclusion` (글자마다), 확정되면 `pair_done` |
  | 관계 확인 | `POST /dev/keyword-relation/stream` | `field` 이벤트: `verdict`·`type` 이 먼저, `reason` 은 글자마다 |
  | 챗봇 | `POST /internal/v1/chat` ([chat-api.md](chat-api.md)) | `delta` 이벤트: 답의 다음 조각 |

  구조화(JSON) 출력은 `app/services/llm/partial_json.py` 의 `JsonStream` 이 쓰이는 대로 읽는다 (조각을 어디서 자르든 같은 이벤트, 이스케이프·유니코드·서로게이트 쌍 처리, 깨진 입력에도 예외 없음).
  **웹 검색 뒤의 구조화 출력은 결과 글이 끝에 한꺼번에 온다** — 모델·effort 와 상관없이 모든 조각이 0.01초 안에 도착했다 (Opus·Sonnet 모두). 일반 글은 검색과 함께여도 2.8~3.5초에 걸쳐 조각조각 온다.
  그래서 새 지식 만들기는 결과를 구조화 출력이 아니라 `submit_knowledge` 클라이언트 도구 호출(`eager_input_streaming`) 로 받는다 (`newknowledge-llm-3`): 도구 입력은 쓰이는 대로 온다.
  실제 한 쌍에서 결론 60조각이 4.4초부터 7.4초까지 이어졌다 (이전: 약 10.6초에 한꺼번에). 도구 입력은 SDK 의 너그러운 파서가 아니라 받은 글 그대로 엄격하게 다시 파싱하고, 끊겼으면 `invalid_output` 이다.
  선별·관계 확인은 검색이 없어서 구조화 출력 그대로 조각조각 온다 (선별 12쌍의 라벨이 2.0초 3개 → 2.6초 6개 → 3.2초 10개 → 3.9초 12개로 늘었다).
  **중단**: 카드의 `중단` 이나 탭을 닫으면 연결이 끊기고, 서버는 다음 알림에서 모델 호출(스트림)을 닫아 검색·토큰을 더 쓰지 않는다. 멈춘 호출은 결과를 캐시에 남기지 않는다.
  결과 카드는 근거 A · 근거 B · 외부 지식(URL) → 결론이고, 버튼은 이해함(그래프에 들어갈 개념을 보여 줌) · 알고 있던 내용(숨김, 브라우저에 기억) · 이해가 안 됨(챗봇에 넘길 컨텍스트를 보여 줌)이다.
  모델은 `AI_PAIR_SCREEN_LLM_*` · `AI_SUGGEST_LLM_*` → `AI_LLM_*` → `ANTHROPIC_API_KEY` 의 기본 모델이다 (웹 검색은 anthropic 제공자만). 두 호출만 노트 내용을 LLM 제공자에게 보내고 (로컬 접속만 받는다),
  결과는 `data/private/cache/pair-screens`, `new-knowledge` 에 캐시한다.
  DB-WAL 노트의 "디스크" 요소(DB 는 buffer pool 에서 페이지를 고친다)와 다른 노트의 "페이지 캐싱" 요소(OS 가 읽은 데이터를 RAM 에 저장한다) 에 MySQL 문서 두 곳을 이어
  "DB 와 OS 가 둘 다 캐시해서 같은 페이지가 메모리에 두 번 올라가는 이중 버퍼링이 생길 수 있고, InnoDB 는 O_DIRECT 로 이를 줄인다" 는 결론이 나왔다.
  새 키워드로 둘지 기존 키워드의 새 개념으로 둘지, 인터넷 URL 을 소스에 넣을지, 외부 지식으로 검증할지는 회의록대로 아직 정하지 않았다 (결과는 `newKeyword` 이름과 `external` 을 따로 둔다).

- **성능** (실제 노트 141개, 이 머신에서 잰 값. 시간·토큰은 한 쌍·한 번씩이라 대략의 크기로 본다):

  | 단계 | 이전 | 지금 | 방법 |
  | --- | --- | --- | --- |
  | 처음 요청 (노트 색인 만들기) | 11.6초 | 2.3초 (다시 켠 서버) | 노트마다 만든 색인을 `data/private/cache/note-entries` 에 둔다 (키 = 노트·원문 해시·방법 버전). 노트 하나를 고치면 그 노트만 다시 만든다 |
  | 후보 찾기, 요소 3,318개 전부 | 6.9초 | 0.57초 | 키워드 이름 trie 한 번 훑기, 정렬 없는 top-k 행렬곱 |
  | 그래프·연결 요청 | 50~130ms | 1~5ms | 증거 수준별 선·이웃 색인 캐시 |
  | 새 지식 만들기 한 쌍 | 21초, 입력 약 2만 토큰 | 18초, 입력 약 3천 토큰 | 기본 검색 도구 `web_search_20250305` (동적 필터링판은 코드 실행 도구 때문에 입력이 6배). 같은 쌍에서 결론·출처 검증 결과가 같았다 |
  | LLM 선별 36쌍 | — | 3.5~6초 (Haiku · Sonnet · Opus 모두) | 한 묶음 10쌍, 묶음끼리 병렬 |

  `newknowledge-llm-3` 는 검색을 한 번으로 제한하고 (한 번에 9개쯤 받고 한 번이 약 9초), 모델이 쓰는 출처 필드를 `url`·`quote` 로 줄였다 (제목은 검색 결과에서 URL 로 가져오고, `reason` 은 ok 가 아닐 때만 쓴다 —
  모델이 쓰는 글의 약 37% 가 줄었다). 같은 5쌍에서 이전 결과(llm-1)와 비교하면 상태가 5쌍 모두 같았고, 결론이 나온 3쌍은 키워드·내용이 같았고 출처 수도 같았다. 검색한 4쌍이 13~19초였다 (이전 18~21초).
  세 번 검색하던 한 쌍(노트와 웹이 달라 가설이 된 쌍)이 한 번으로 줄었다. 표본이 작아서 품질이 같다고 단정하지는 않는다.
  새 지식 만들기는 모델·effort·도구를 바꿔도 15~21초였다 (검색 왕복과 출력이 대부분). Sonnet 은 effort low 나 동적 필터링판에서 검색을 건너뛰고 "새로 말할 것이 없다" 고 답한 적이 있어 기본으로 쓰지 않는다.
  선별 모델의 기본은 Haiku (가장 싸고, 275쌍 시험에서 정밀도가 가장 높았다). 속도 차는 없다. 세 모델의 useful 판정은 36쌍에서 서로 거의 겹치지 않았다 (일치 44~64%, useful 겹침 1~2쌍) — 선별 결과는 참고로 본다.
  검색 도구는 `AI_SEARCH_TOOL` 로, 모델은 `AI_PAIR_SCREEN_LLM_MODEL` · `AI_SUGGEST_LLM_MODEL` 로 바꾼다. 전체 흐름(후보 → 선별 → 만들기)의 시간은 거의 만들기 한 번(약 18초, 상위 3개는 병렬)이다.

## 쓰임

- 사용자용 그래프의 간선: 같은 키워드에 개념을 넣은 두 페이지를 잇는다. `Keyword.note_ids()` 가 그 페이지 집합이다.
- 기능용 그래프의 간선은 키워드 사이 "관계가 있다" 정도이고 유형은 쓰지 않을 가능성이 높다 (회의록). 이 문서는 노드만 정의한다.
- 새 지식 생성의 입력은 키워드가 아니라 그 안의 개념 P·Q 다. 생성된 개념의 `sources` 에는 P·Q 의 페이지가 반드시 들어간다.
