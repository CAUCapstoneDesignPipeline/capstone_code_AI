# 연결 후보 ④ · 설명 ⑤ 평가

설계 `concept-pipeline.md` 7장의 평가 중 연결 후보와 설명에 해당하는 것. 결과 파일·표는 노트 내용이 들어 있어
`data/private/gold/` 에만 둔다. 숫자는 개발 노트 141개, 정답은 **검토 전 초안** 기준이다.

## 정답 자료 (2026-10-28 확장)

| 자료 | 이전 | 지금 | 만든 방법 |
| --- | --- | --- | --- |
| 정답 개념 노트 | 8개 (249줄) | **26개 (972줄)** | 새 18개는 추출 결과를 보지 않고 표시 기준만으로 초안. 모두 `split=test` |
| 정답 노트 쌍 | 9쌍 | **27쌍** | 질의 노트 24개 × (S 상위 3 + TF-IDF 상위 3 + 무작위 2) 풀 144쌍을 판정 (어느 방법이 낸 쌍인지 모르게) |
| 판정한 쌍 (yes/no) | 없음 | **144쌍** (yes 23) | 위 풀. 상위 3 개 정밀도에 쓴다 |

- 새 정답은 모두 `draft` 다. 사람이 검토하면 `reviewed` 로 바꾼다.
- AI 2차 검토 (`review=ai-2nd-pass`): 다른 AI 검토자가 개념 26개 노트 전부(972 → 967줄, core 586 → 602)와 판정 쌍 53개
  (yes 23 전부 + no 30)를 원문을 읽고 다시 봤다. 쌍 판정은 53개 모두 일치했다. 사람 검토를 대신하지 않으므로 `status` 는 `draft` 그대로다.
- 풀의 무작위 쌍 40개는 모두 no 였다. 두 방법이 함께 놓친 이어진 쌍이 많지는 않다는 뜻이지만, 정답 쌍 대부분(23개 중
  20개)이 S 상위에서 왔으므로 S 의 Recall@k 는 실제보다 높게 나온다.
- 목차 페이지 7개(링크 모음)는 `topics.csv` 에서 주제를 `목차` 로 바꿨다.

### 확장 후 결과 (`uv run python eval.py`)

| 지표 | 값 [95% 구간] | 단위 수 |
| --- | --- | --- |
| 개념 재현율 (core), dev (규칙을 고치며 본 노트) | 86% [77–92%] | 노트 8 |
| 개념 재현율 (core), **test (처음 보는 노트)** | 84% [78–89%] | 노트 18 |
| 개념 정밀도, dev | 62% [58–70%] | 노트 8 |
| 개념 정밀도, **test** | **42% [38–46%]** | 노트 18 |
| 노트 쌍 Recall@10 (다른 주제) | 96% [91–100%] | 질의 54 |
| 노트 쌍 MRR | 0.62 [0.53–0.70] | 질의 54 |
| **상위 3 개 중 이어진 쌍 비율 (precision@3)** | **33% [18–50%]** | 질의 20 |

- 재현율은 처음 보는 노트에서도 유지된다. 정밀도는 처음 보는 노트에서 20%p 낮다. 규칙을 dev 노트에 맞춰 고친 효과가
  부풀려져 있었다는 뜻이다. 다음 개선은 정밀도이고, test 노트의 '정답 밖' 목록은 보지 않고 dev 노트로만 고친다.
- **규칙을 dev 노트로만 고친 효과 (2차 검토한 정답, 같은 자료로 비교)**: 소유격 이름 복원·영어 문장 제목 제거·앞뒤 꾸밈말 제거로
  dev 정밀도 62% → 67%, **test 정밀도 42% → 43%** (구간 안), 재현율은 그대로다. dev 에서 본 오답 유형을 고치는 규칙은
  처음 보는 노트에 거의 옮겨지지 않는다. test 정밀도를 올리려면 개별 규칙보다 선택 기준(점수 문턱값, 노트당 개수) 쪽을
  dev 로 정하고 test 로 한 번 확인하는 편이 낫다.
- 사용자에게 보이는 연결 상위 3 개 중 이어진다고 판정된 것은 3 개 중 1 개 남짓이다 (2차 검토 뒤 39% [22–59%], 질의 17). 정답 쌍은 대부분 찾지만(Recall@10 96%)
  상위에 관계없는 노트도 섞인다.

## 한 번에 재기 (`uv run python eval.py`)

①·④·⑤ 를 한 번에 잰다 (`uv run ai eval` 과 같다). 노트 색인은 한 번만 만들고 6초쯤 걸린다. LLM 을 부르지 않는다.

- **신뢰 구간**: 값마다 bootstrap 95% 구간 (노트·질의·쌍 단위, seed 고정). 정답 쌍이 9개라 Recall@10 89% 의 구간은
  72–100% 다. 구간 안의 변화는 개선이라고 하지 않는다.
- **dev / test**: 정답 노트를 hash 순으로 dev 5 · test 3 으로 나눈다 (정답 CSV 에 `split` 칸을 두면 그것을 따른다).
  규칙을 고칠 때는 `ai concepts eval` 로 dev 노트만 들여다보고, test 는 보고서에서만 본다. 지금 8개 노트는 모두 규칙을
  고치며 본 적이 있어 test 도 깨끗하지 않다. 새로 표시하는 노트는 `split=test` 로 둔다.
- **비교**: 보고서가 `data/private/eval/` 에 쌓이고, 새 값이 지난 보고서의 95% 구간 밖이면 🔻 나빠짐 / 🔺 좋아짐 으로 표시한다.
  `--no-save` 는 보고서를 쌓지 않는다. 검토한 정답이 없으면 초안으로 재고 그렇다고 적는다.

## 처음 보는 노트에서의 개념 추출 (2026-10-28)

dev 노트를 15개 더 표시해 23개(주제 11개 모두)로 늘리고, test 18개는 끝까지 열어 보지 않았다.
dev 오답을 유형으로 나눠 보면(`experiments/concept_precision/diagnose.py`) 낱말 하나하나보다 구조가 문제다:
긴 노트는 정답의 2배쯤을 뽑고, 신뢰도 0.2–0.3 은 정답률 29–39%, 구조 근거 없이 TF-IDF 로만 뽑힌 한국어 낱말 하나,
영어·한국어 섞인 조각(`MDP의 해답`), 흔한 낱말이 약하다. 결정적 선택 규칙(신뢰도 문턱값, 흔한 낱말·섞인 조각 빼기, 길이당 상한)은
dev 에서 재현율을 내준 만큼만 정밀도가 올랐다 (재현율 81% 에서 정밀도 55%, 75% 에서 58%).

LLM 이 후보를 **빼기만** 하는 `extract-hybrid-3` (`concept-filter-2`, effort low, 노트당 한 번, 캐시):

| | dev 정밀도 | dev 재현율 | **test 정밀도** | **test 재현율** |
| --- | --- | --- | --- | --- |
| `extract-det-3` | 51% | 84% | 43% [39–47%] | 85% |
| `extract-hybrid-3` | 81% | 83% | **73% [66–79%]** | **84%** |

- test 는 이 표를 만들 때 한 번만 쟀다 (filter prompt 는 test 노트를 보지 않고 썼다).
- 재현율을 잃지 않고 정밀도가 30%p 오른다. 노트당 약 4초 (41개 노트 2분 44초, 캐시 없이).
- 첫 형식(후보마다 keep/drop)은 후보가 많은 긴 노트에서 LLM 제한 시간(90초)을 넘었다. 뺄 후보 번호만 답하게 바꿔 해결했다.

## ④ 정답 노트 쌍 Recall@k (`uv run ai links eval`)

정답 쌍 9개(질의 18개). 설계대로 다른 주제의 노트만 후보로 본다.

| 방법 | R@1 | R@5 | R@10 | R@20 | MRR |
| --- | --- | --- | --- | --- | --- |
| S (Adamic-Adar, 전체) | 33% | 78% | 83% | 89% | 0.52 |
| **S (다른 주제)** | 56% | 83% | 89% | 89% | 0.68 |
| TF-IDF 코사인 (다른 주제, 기준선) | 56% | 83% | 89% | 89% | 0.69 |
| S·N^1 (주제 새로움) | 56% | 83% | 89% | 89% | 0.68 |

- 통과 기준 Recall@20 50% 이상을 넘는다. `WAL ↔ 저널링` 은 1위.
- 정답 쌍이 9개뿐이라 TF-IDF 기준선·새로움 가중과 차이가 나지 않는다. 새로움 N 은 순위를 바꾸지 못했다 (α=2 는 조금 나빠짐).
- 못 찾는 쌍: DP ↔ MDP (MDP 노트에 DP 라는 말이 없다).

## ④ 숨겼다 다시 찾기 (`uv run ai links refind`)

정답 표시 없이 하는 결정적 평가. 한 노트의 한 문장에 함께 쓰인 개념 쌍 (A, C) 중 다른 노트 어디에도 함께 쓰이지 않은
쌍을 seed 로 고정해 200개 고르고, 그 노트를 숨긴 뒤 다른 노트들의 문장 동시 출현 그래프에서 A 로 물었을 때 C 의 순위를 본다.
A 와 이미 함께 쓰인 개념은 후보에서 뺀다.

| 방법 | R@1 | R@5 | R@10 | R@20 | MRR |
| --- | --- | --- | --- | --- | --- |
| A-B-C (Adamic-Adar, 허브 B 제외) | 2% | 4% | 6% | 10% | 0.03 |
| 인기도 기준선 (C 가 나오는 노트 수) | 1% | 4% | 5% | 8% | 0.03 |

- 개념 수준의 A–C 는 노트 쌍보다 훨씬 어렵다 (후보가 개념 수천 개). A-B-C 가 기준선보다 조금 낫지만 차이가 작다.
- 이 수치는 "개념 하나로 다른 개념을 맞히기" 이고, 실제 제안은 노트 쌍 ④ 를 먼저 고른 뒤 그 안의 관계 경로만 보므로
  범위가 훨씬 좁다. 숨긴 쌍 대부분은 한 노트 안의 우연한 동시 출현이라 다시 찾을 근거가 원래 없는 경우도 많다.
- 같은 seed 는 같은 쌍을 고른다. 추출이 바뀌면 고르는 쌍도 바뀌므로 비교는 같은 commit 끼리 한다.

## ⑤ 설명·검증의 사람 판정 일치율 (`experiments/explanation_eval/human_eval.py`)

목표: 시스템 판정과 사람 판정의 일치율 80% 이상.

1. `sample --notes <노트 이름> …` 이 노트마다 새 지식 제안을 만들어 `data/private/gold/explanations.csv` 에 쓴다
   (설명 생성·관계·간선·설명 검증 LLM 을 부른다. 노트마다 설명 `--per-note` 개).
   제안(candidate·hypothesis)과 설명 검증에서 제외된 것(rejected)을 결론 문장·근거와 함께 한 줄씩 적는다.
   시스템 판정은 표에 없고 `explanations-key.csv` 에 따로 쓴다. 줄 순서도 섞는다 (판정을 보고 표시하면 일치율이 부풀려진다).
2. 사람이 `human` 칸에 표시한다: `valid`(근거에서 도출되고, 노트에 그대로 있지 않고, 구체적이다) /
   `invalid`(틀렸거나, 이미 노트에 있거나, 뻔하다) / `unsure`. 열쇠 파일은 열지 않는다.
3. `score` 가 일치율, candidate 정밀도(통과시킨 제안 중 valid 비율), 제외 정확도(제외한 것 중 invalid 비율)를 낸다.
   시스템 판정은 candidate → valid, hypothesis → unsure, rejected → invalid 로 본다.

아직 사람 표시가 없어 수치는 없다.
