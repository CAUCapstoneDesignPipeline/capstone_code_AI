# 관계 추출 모델 비교 — 평가

한 노트 안의 개념 사이 관계(유형 8개 + 방향 + 근거)를 어떤 방법으로 뽑을지 같은 정답·같은 채점으로 견줬다. **개념은 정답 개념으로 고정**해 관계 추출만 잰다 (개념 추출의 오차가 섞이지 않게).
정답과 판정이 모두 AI 가 만든 것이라 사람이 검토하기 전의 수치다 ("읽을 때 주의" 참고).

## 정답과 채점

- **정답** (`experiments/relations/gold.py`): 정답 개념이 있는 노트 59개(과목 dev 23 · test 18, 논문 리뷰 18)에서 Opus 5.5 가 초안을 쓰고 Sonnet 5.5 가 검토했다 (받아들임 90~93%, 검토자가 더한 것 포함).
  관계 1,087개 (노트당 20~27개). 판정 기준은 "노트가 그렇게 말하는가"다 (상식으로 만들지 않는다). **약 60% 는 문장이 아니라 제목·목록·표 구조가 드러내는 관계**다 (예: "## Level 1: Read Committed" → Read Committed is_a Isolation Level).
- **정답이 불완전하다.** 정답에 없는 Sonnet 의 예측 관계를 Opus 가 노트에 비춰 판정하니 새 쌍의 69~78% 가 노트가 실제로 말하는 관계였다. 정답만으로 채점하면 정밀도가 42~46% 로 낮게 나오지만 어림한 실제 정밀도는 74~81% (유형까지 같음) · 85~88% (어떤 관계든) 였다.
- **풀링 판정** (`pool.py`, `pooled_eval.py`): 모든 방법의 예측 중 정답에 없는 것을 Opus 가 한 번씩 판정해 저장하고, 맞는 관계 집합 V = 정답 ∪ 판정자가 맞다고 본 것 (판정자가 고른 유형·방향)으로 모든 방법을 채점한다.
  strict = 쌍·유형·방향이 V 에 든 것, pair = 두 개념 사이 관계가 있다고 맞힌 것. V 는 방법을 더할 때마다 커지므로 방법은 같이 비교한다 (아래는 지금까지의 판정 전체 기준).
- **후보 쌍** (`candidates.py`): 같은 문장 ∪ 같은 절(가장 안쪽 제목 아래) ∪ 제목에 나온 개념 ↔ 그 제목 절 안의 개념. 정답 쌍의 98% 를 담으면서 모든 쌍의 36~39% 만 남긴다 (노트당 과목 260~360쌍, 논문 65쌍).
  **기존 서비스의 후보 쌍(같은 문장·언급 3칸 안·사이 40자 이하)과 구조 규칙은 정답 쌍의 49~58% 에만 닿는다** — 문장 속 쌍만 보는 방법은 재현율 상한이 거기다.

## 결과 (strict F1 / pair F1, dev · test · 논문 리뷰)

모두 같은 판정 풀 기준 (맞는 관계 집합 V: dev 1,623 · test 1,719 · 논문 332).

| 방법 | 지연 (노트 하나) | strict F1 | pair F1 |
| --- | --- | --- | --- |
| 규칙 + 구조 (지금 서비스의 관계, LLM 없음) | 약 10 ms | .02 / .02 / .02 | .04 / .03 / .03 |
| 구조·위치 특징만 학습 (Decisions 없음) | 수 ms | .18 / .15 / .11 | .56 / .57 / .52 |
| 규칙 + 구조 + LLM typer (Sonnet low, 서비스의 hybrid 와 같은 방식) | 중앙값 13~15 s (논문 4 s) | .24 / .26 / .39 | .34 / .36 / .53 |
| gpt-5.4-mini 만으로 (LLM-only) | 2~4 s | .31 / .26 / .39 | .59 / .55 / .66 |
| Decisions 객관식, 선택지가 A·B 라는 일반 표현 (임계값 0.55) | 중앙값 0.9 s | .34 / .33 / .30 | .58 / .59 / .59 |
| Decisions 객관식, 선택지에 실제 표기를 넣음 (임계값 0.4) | 중앙값 0.9 s · 요청 1개 | .37 / .39 / .38 | .59 / .61 / .62 |
| **구조 특징 + Decisions(표기를 넣은 선택지) 확률을 학습한 분류기** (59노트 교차검증) | **약 1 s** | **.43 / .41 / .40** | **.66 / .66 / .64** |
| Haiku 5.5 만으로 | 7~21 s | .49 / .48 / .53 | .66 / .62 / .70 |
| **Sonnet 5.5 만으로** (노트 + 개념 목록 → 관계) | **3~7 s** | **.56 / .53 / .62** | **.71 / .69 / .77** |

- **LLM 이 노트 전체를 읽는 방법이 가장 낫다.** Sonnet 이 정답의 79% 를 찾고 낸 관계의 78~82% 가 맞다 (strict 정밀도). 구조로 드러나는 관계를 잡는 것은 이 방법뿐이다 (Decisions 쌍 분류도 구조 후보 쌍을 쓰지만 쌍마다 따로 묻는다).
- 지금 서비스의 규칙은 노트당 1개쯤만 내서 (정밀도 50~83%) 재현율이 1% 이고, LLM typer 를 붙여도 (후보 쌍이 문장 속 쌍뿐이라) strict F1 이 .24~.39 에 그치며 13초 넘게 걸린다.
- **Decisions 로 빠른 쪽이 열린다.** 쌍마다 객관식 질문 하나(요청 하나, 노트 원문은 한 번만 읽힌다)로 약 1초에 strict .37~.39, 학습한 분류기를 얹으면 .40~.43 이다: Sonnet 의 70~75% (논문 65%), pair 는 93~97%.
  유형·방향을 맞히는 것이 병목이다 (쌍은 .6 쯤 찾지만 유형까지 맞는 것은 .37~.43). 질문 문구가 영향이 크다: 선택지에 실제 표기를 넣으면 (A·B 대신) strict F1 이 .02~.08 올랐다.
  "노트가 관계를 말하는가" predicate 질문을 더해 평균을 내 봤지만 같았다 (strict .35 / .36 / .31, 모든 쌍에 TRUE 를 내는 쪽으로 쏠려 보정이 안 된다).
- **트리·MLP·인코더** (학습한 분류기의 모델 종류): 분류기는 부스팅 트리다. 같은 특징 위에서 MLP 는 키워드 학생에서 트리보다 낮았고 (`docs/eval/concept-student.md`) 관계에서는 다시 재지 않았다.
  문맥 인코더(multilingual-e5-small 을 노트 전체에 한 번 돌려 두 개념의 언급 벡터를 얻고 [A, B, A×B] 를 로지스틱 탐침으로 교사 관계에 맞춘 확률)를 특징으로 더해도 strict F1 이 .42 / .41 / .38 로 더하기 전(.43 / .41 / .40)과 같거나 낮았다 (59노트 교차검증, 노트 단위 중첩 탐침).
  탐침만으로는 낸 관계의 75% 가 판정되지 않았고 (판정 비용이 소진되어 더 못 했다) 판정된 것만 보면 정밀도가 낮았다. 얼린 인코더 벡터는 관계의 유형·방향을 가르는 데 쓸 만한 정보를 주지 않았다. 인코더를 미세조정하는 것(개체 표지를 넣은 cross-encoder)은 하지 않았다.
- 구조·위치 특징만으로는 쌍은 .56 정도 찾지만 유형·방향을 몰라 strict .11~.18 이다. Decisions 확률이 그 유형 판단을 채운다.
- Haiku 지연은 한 번에 4개씩 보냈을 때의 값이라 흔들린다 (Sonnet 보다 느린 것은 출력이 길어서일 수 있다).

## 출고한 빠른 관계 profile: `pairs-1`

지연을 최우선으로 두고 괜찮은 성능이면 되는 쪽의 선택이다 (strict F1 은 Sonnet 의 약 70~75%, 지연은 약 1/4~1/8). `app/services/relations/pairs.py`, 모델 `pairs-1.json` (2 MB, numpy 로 계산, 같은 입력·같은 판정이면 항상 같은 결과).

- **흐름**: 후보 쌍(`candidates.py`) → Decisions 객관식 요청 하나(노트 원문은 한 번, 쌍마다 질문 하나, 선택지에 실제 표기를 넣음, 400쌍까지) → 구조·위치 특징 + 선택지 확률을 학습한 트리 둘(관계가 있는가 · 있다면 유형·방향) → 임계값 0.2 → 관계.
  **근거**는 두 개념이 같은 문장에 가장 가까이 나온 곳의 그 문장이고 (같은 문장이 없으면 가장 가까운 두 언급이 든 문장·제목 줄), 코드가 원문에서 그대로 자르므로 quote 는 항상 원문 slice 다. LLM-only 에는 없던 부분이다.
- **profile**: `extract-student-pairs-1` (학생 개념 + 이 관계, 개념 단계 약 0.1초 + 관계 단계 약 0.8초), `extract-student-decisions-pairs-1` (Decisions 개념 판정 + 이 관계, 약 0.8초 + 0.8초, 두 요청이 차례로 나간다). 둘 다 **기본 꺼짐**(`AI_DECISIONS_JUDGE=1`). 규칙·구조 관계는 쓰지 않는다 (strict F1 .02).
- **성능**: 위 표의 분류기 행과 같다. 노트 단위 5겹 교차검증, 임계값은 dev 예측에서 골랐다 — strict F1 .43 / .41 / .40, pair F1 .66 / .66 / .64. 출고 모델은 59개 노트 전체로 다시 학습했다 (교사는 Sonnet LLM-only, 캐시된 응답).
- **지연** (출고 코드를 정답 노트 59개에서 실제로 불러 잼, 개념은 정답 개념, `eval_pairs.py`): 관계 단계 중앙값 **0.80초**, p90 1.25초, 최대 1.45초 (dev 0.87 · test 1.06 · 논문 0.48초). 노트당 후보 쌍 평균 258 · 359 · 65개, 낸 관계 평균 56 · 65 · 21개.
  지연은 쌍 수에 거의 늘지 않는다 (요청 하나). 쌍은 노트당 800개까지만 판정한다 (`MAX_PAIRS`, 같은 문장·제목 쌍과 가까운 쌍을 먼저) — 개념이 아주 많은 노트의 비용을 묶는다. 요청 하나는 입력 토큰 약 6만이라 분당 한도(TPM)를 쓴다.
- **한계**: 임계값 0.2 는 탐색한 격자의 가장자리라 (그 아래 예측은 판정하지 않았다) 더 낮은 값이 더 나을 수 있다. 낸 관계가 많은 편이다 (노트당 정답 20~27개에 56~65개, 정밀도 37~50%). 교사가 Sonnet 이라 Sonnet 의 오류를 따라 한다.
  실제 서비스에서는 개념 추출의 오차가 더해진다. 노트 원문이 OpenAI 로 나간다. 질문 문구·선택지·특징·임계값이 모델의 일부라 바꾸면 `PROMPT_VERSION` 과 profile id 를 함께 올린다. 학습은 `train_pair.py` (`--threshold`, `--write`), 파일의 특징 목록이 코드와 다르면 로드를 거부한다.
- 정확도가 더 필요하면: Sonnet LLM-only (strict .56 / .53 / .62, 3~7초) 를 두 번째 단계로 둔다 (아직 서비스에 넣지 않았다. 근거는 같은 방식으로 코드가 찾아야 한다).

## 읽을 때 주의

- **정답·판정이 AI 가 만든 것이다** (사람 검토 전). 판정자(Opus)가 정답 초안을 쓴 모델과 같고 Sonnet 이 검토에 참여했으므로 Claude 계열 방법이 정답과 판단이 닮아 유리하다. 독립적인 읽기로 gpt-5.4-mini 를 같이 쟀지만 작은 모델이라 낮은 점수가 그 탓인지 가려지지 않는다.
  강한 비-Claude 모델(gpt-5.5, Gemini Pro)은 지연이 10~40초라 이 비교에 넣지 않았다. 정답 몇십 개를 사람이 확인해야 한다.
- 풀링 판정은 풀에 낸 방법에 유리하다 (방법을 더하면 V 가 커져 다른 방법의 재현율이 내려간다). 순위는 풀이 커져도 바뀌지 않았지만 값은 바뀐다.
- 학습한 분류기는 59개 노트로 노트 단위 5겹 교차검증한 값이고 임계값을 dev 예측에서 골랐다. 교사(Sonnet 의 관계)가 정답이 아니므로 교사의 오류를 따라 한다. 학습 노트를 늘리면 나아질 수 있으나 재 보지 않았다.
- 개념은 정답 개념이다. 실제 서비스에서는 개념 추출의 오차가 더해진다. 응답에는 관계마다 근거 구간이 있어야 하는데 LLM-only 는 근거를 내지 않는다 (코드가 원문에서 두 개념이 함께 나온 문장·제목 줄을 찾아야 한다, 아직 구현하지 않았다).
- 유형 구분 자체가 흐리다 (같은 쌍에 used_for 와 requires 가 다 성립하는 식). pair 점수가 더 믿을 만하다.

## 재현

```bash
uv run --env-file .env python experiments/relations/gold.py                       # 정답 만들기 (Opus 초안 + Sonnet 검토, data/private/gold-relations)
uv run --env-file .env python experiments/relations/eval.py --methods reach rules   # 후보 쌍이 닿는 범위, 규칙 기준선
uv run --env-file .env python experiments/relations/adjudicate.py                  # 정답에 없는 예측의 표본 판정 (정답이 불완전한 정도)
uv run --env-file .env python experiments/relations/decisions_pairs.py             # Decisions 객관식 (쌍마다 질문 하나)
uv run --env-file .env python experiments/relations/pooled_eval.py --methods rules hybrid:anthropic:claude-sonnet-5-5:low llm:anthropic:claude-sonnet-5-5 llm:anthropic:claude-haiku-5-5 llm:openai:gpt-5.4-mini decisions:0.55
uv run --env-file .env python experiments/relations/pair_model.py --named [--no-decisions]  # 학습한 쌍 분류기 (교차검증, --named = 선택지에 표기를 넣은 질문)
uv run --env-file .env python experiments/relations/train_pair.py --threshold 0.2 --write   # 출고 모델 (pairs-1.json) 학습·내보내기
uv run --env-file .env python experiments/relations/eval_pairs.py                  # 출고 코드를 실제로 불러 지연 재기
```
