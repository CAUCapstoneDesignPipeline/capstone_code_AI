# 조건부 결론 (R1·R2) 평가

상태: 2026-10-29 첫 측정. 사례는 엔진을 만들며 함께 쓴 dev 사례뿐이라 **독립된 시험이 아니다** (안건 6 의 60사례 테스트는 아직 없다).

## 1. 대표 사례 (docs/team/data, 9사례)

`uv run ai derive` / `uv run ai derive --auto --sound`

| 사실 | soundness | 결론 정밀도 | 결론 재현율 | 잘못된 확정 (음성) | 상태 일치 |
| --- | --- | --- | --- | --- | --- |
| 사람이 적은 것 | 끔 (8사례) | 100% (11/11) | 100% (11/11) | 0% (0/3) | 100% (16/16) |
| LLM 추출 (`facts-llm-1`) | 켬 (9사례) | 100% | 100% | 0% | 100% |

- LLM 추출은 같은 대상을 다른 key 로 부를 수 있다 (`binary_heap` ↔ `binary_min_heap`). `/facts` 에 `knownSubjects` 를 주면
  뒤 노트가 앞 노트의 key 를 따른다. 사례 점수는 `cases.json` 의 aliases 로 맞춘다.
- 처음 프롬프트는 주체 이름을 "인덱스 있는 버전" 처럼 가리킴 말로 뽑아 결론 문장이 어색했다 → 온전한 이름을 쓰게 고쳤다.
- `wrong-premise-sorted-array`: 노트가 "정렬 배열 삽입 O(1)" 로 잘못 적었다. 규칙은 O(V + E) 를 통과시키지만 soundness 판정이
  "삽입·키 줄이기는 원소를 옮겨야 해서 O(n)" 이라며 기각했다. R1(정렬 배열로 우선순위 큐를 쓸 수는 있다)은 맞는 결론으로 남는다.

## 2. 실제 노트 (data/private/notes, 탐색)

`uv run python experiments/derivation/real_notes.py --sound`. 141개 중 복잡도를 말하는 32개, 기대 결과 없음.

| 항목 | 값 |
| --- | --- |
| 사실 | 91개 (uses 27, requires 20, stated_result 18, needs_op 12, op_cost 8, implements 5, size_bound 1). 원문에 없는 quote 0 |
| 도출 | R1 결론 1 · R1 보류 8 · R1 이미 앎 2 · R2 보류 3 · R2 결론 0 |

- **실제 노트는 연산 횟수를 거의 쓰지 않는다.** "다익스트라는 우선순위 큐를 쓴다", "크루스칼은 Union-Find 로 O(E log E)" 처럼
  쓰고 "키 감소 최대 E번" 같은 전제는 없다. 그래서 R2 는 모두 보류다. 모델 상식으로 채우지 않는다는 결정대로다.
- 노트가 결론 자체를 쓴 경우(`stated_result` 18개)는 이미 앎으로 처리되고 새 결론이 되지 않는다.
- 연산 하나만 겹치는 R1(배열 ↔ 조인의 순서 있는 집합 "찾기")은 맞지만 쓸모없는 결론이었다 → 자료 구조가 그 역할의 구현이라고
  노트에 없으면 필요한 연산 둘 이상을 모두 제공할 때만 후보로 바꿨다.
- 남은 결론 하나: "Red-Black tree 로 Indexed Nested Loop Join 의 순서 있는 집합을 구현할 수 있어요" (DB 노트 + OS 스케줄링 노트의 CFS).
  soundness 는 sound. 유용한지는 사용자 판단이다.

**시연에 주는 뜻.** 사용자 노트로 R2 결론이 나오려면 노트에 연산 횟수·연산 비용·크기 상한이 적혀 있어야 한다. 시연은
`docs/team/data` 의 노트처럼 이 정보를 쓴 노트로 하고, 실제 노트에서는 "필요한 전제가 노트에 없어요" 가 대부분임을 한계로 적는다.
